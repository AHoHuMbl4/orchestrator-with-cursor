# Декомпозиция: как оркестратору понять задачу и разрезать её

Читать оркестратору ПЕРЕД нарезкой любой нетривиальной задачи и при каждом
replan. Синтез проверенных практик (планировщики spec-kit/wshobson, правила
Anthropic multi-agent, DAG-подходы типа LLMCompiler — источники в конце).

## 0. Цель, критерий и TODO — до нарезки

1. Сформулируй цель одной фразой и **глобальный критерий приёмки** —
   измеримый (тест/файл/число/рубрика). Нет измеримого «готово» — не
   декомпозируй: сначала добудь критерий.
2. Границы: что НЕ трогать; какие ресурсы/файлы в игре.
3. Запиши в compass: цель, критерий, границы И **TODO-чеклист** — по строке
   на подзадачу/волну (видно что сделано, что в работе, что осталось).
   Каждая закрытая строка TODO = принятая оркестратором подзадача.
   Нудж сверяется с TODO, не с абстракцией.

## 1. Gate неоднозначности (до старта, один раз)

Порядок решения (приоритет сверху вниз):
1. Мета-вопросы (о сессии/параметрах/уточнение формулировки) — ответь сам,
   без исполнителей и без декомпозиции.
2. **Неоднозначность:** нет предмета и/или критерия готовности — СТОП,
   **1–3 коротких нумерованных вопроса** владельцу; декомпозиция вслепую
   запрещена. То же при ПРОТИВОРЕЧИИ или если ответ меняет разбиение/
   критерий/границы — задай вопросы и жди.
3. Владельца нет на связи, а решение не блокирует безопасность/границы —
   зафиксируй Assumptions (явно помеченные допущения) в compass и продолжай.
Никогда не задавай вопросов исполнителям: всё нерешённое — либо вопрос
владельцу (п.2), либо допущение (п.3).

## 2. Нужен ли split вообще? (проверь по чек-листу)

ОДИН исполнитель, если выполняется хоть одно:
- (а) один артефакт / один файл-кластер;
- (б) шаги жёстко последовательны и делят изменяемое состояние (даже если
  задача «гигантская» — режь её на последовательные шаги ОДНОГО исполнителя
  с фиксацией подшагов, а не на параллельных);
- (в) задача — простой факт/короткий ответ/один критерий;
- (г) задача — диалог с владельцем (нет артефакта — нет исполнителя).

НЕСКОЛЬКО — только если есть независимые направления, риск переполнения
контекста или явный read-only параллелизм (поиск/ревью). Масштаб: тривиальное
— 1; сравнение по 2–4 осям — 2–4; широкий research — больше, но с явными
ролями. Типично 3–7 подзадач; не дроби бухгалтерию.

Артефакт всегда обязателен, кроме чисто диалоговых ответов (мета-вопросы):
оркестратор принимает замером по файлу; «просто ответ в чате» допустим
только для мета-вопросов п.1.

## 3. DAG подзадач

1. Узел = **одна ответственность** + владелец файлов/области + вход/выход.
2. Ребро = зависимость (данные/порядок). Циклы запрещены.
3. Независимость для параллели: разные файлы/области И нет незакрытых
   зависимостей. Пишущие узлы с пересечением файлов — слить или
   сериализовать (пишет один). Пишущие задачи — по одной на области.
   `parallel_per_task` применяется к READ-ONLY задачам (поиск/аудит/
   исследование — N слепых исполнителей для перекрёстной сверки).
   Пишущая задача — всегда ОДИН исполнитель; проверка множественностью
   идёт ПОСЛЕ — волной критиков. Исключение — spike-режим (2-3
   конкурирующие реализации архитектурно значимого решения, каждая в
   своей ветке, выбор за оркестратором+критиками) — только по явному
   решению, не по дефолту параметра.
4. **КАРДИНАЛЬНО: одна маленькая задача = один агент.** Никогда не пихай
   в одного исполнителя «сделай A, потом B, заодно C» — это ловушка №4
   (поздние задачи делаются хуже). В карточке «и A, и B» = две карточки,
   два исполнителя. Карточка каждой подзадачи (это промт исполнителю — из
   роли): цель; точные пути чтения/записи; что НЕ трогать; **acceptance
   criterion** (проверяемый: Given/When/Then, команда, ≥N фактов с URL,
   diff-критерий); АРТЕФАКТ — путь файла результата
   (`.orchestration/sessions/<sid>/runs/<id>/artifact.md`); роль из
   `roles/_index.md`.

**Зависимости (дешёвая альтернатива полному DAG):** если задача B использует
результат A — это ребро: B запускается только после принятия A (волной позже).
Параллелить можно только задачи без рёбер и без пересечения файлов
(«Правь ТОЛЬКО...»). Машиночитаемый `depends_on` в state НЕ заводим — план и
рёбра держит оркестратор в TODO compass.


## 3.5. Валидация декомпозиции (до запуска исполнителей)

После того как DAG и карточки готовы — ПЕРЕЧИТАЙ compass и проверь:
1. Каждая подзадача напрямую ведёт к глобальному критерию? (подзадача,
   которая «вообще полезна», но не приближает к критерию — выкинуть)
2. Нет дыр: покрытие критерия полное? (если критерий «10 моделей», а
   подзадач на 6 — добавить)
3. Нет дублей: две подзадачи делают одно и то же? (слить)
4. Формулировка каждой подзадачи самодостаточна для исполнителя с нулевым
   контекстом? (перечитай карточку глазами исполнителя, который не видел
   исходную задачу)

Если хоть один пункт «нет» — переделай декомпозицию, потом запускай.

## 3.6. Фундамент — подготовка до волн (обязательно)

Перед ЛЮБОЙ пачкой, по порядку:
(а) Gate неоднозначности (§1) — иначе СТОП.
(б) Декомпозиция + валидация (§2–3.5); ориентир 3–7 подзадач, не дроби
    бухгалтерию.
(в) Роль по каскаду (SKILL) — для КАЖДОЙ подзадачи.
(г) Критики: для каждого артефакта — критерий приёмки и рамка домена в
    промт (скептик с конкретным критерием, не «проверь generally»).
(д) Прогноз прогонов (подзадачи × критики × круги + синтез) и порог
    `execution.ask_before_runs` (см. SKILL Preflight-бюджет).

## 3.7. Иерархия больших проектов

**Вход новой сессии (диск-first).** Новая сессия командующего начинается
ритуалом `python3 <kit>/bin/session-entry.py --session <sid>`: брифинг с
диска (версия кита, PROJECT.md, handoff, фронты, компас) + шаблон
стартового промпта; история старого чата не восстанавливается.
**HANDOFF** — `.orchestration/handoff.md` (лимит **2000** символов): Цель /
Сделано / Решения / Провалы / Текущие фронты / Шаги восстановления /
версия кита на паузе; обновляет командующий на границах волн и перед
закрытием сессии.

Гейт `orchestration.hierarchy`: **off** — иерархия ЗАПРЕЩЕНА, всегда
плоский режим (один оркестратор, обычные волны), даже при больших пачках
(контекст — выжимки/артефакты на диске); **auto** (по умолчанию) —
эвристика (прогноз >~30 прогонов / >3 волн / проект с нуля с несколькими
блоками); **on** — предпочитать: любая задача, декомпозируемая на 2+
самостоятельных блока, идёт через фронты (граф+генералы+наблюдатели);
тривиальные одно-блочные — плоско; явное указание владельца в диалоге
перекрывает параметр до конца задачи (зафиксировать в compass). При
активной иерархии — «оркестратор оркестраторов» (компакт — SKILL);
уровни ниже — только когда иерархия активна.
**PROJECT.md** — главный документ, обязательный артефакт проекта (корень, ≤1 стр): Цель;
Архитектура (до 5 строк); Карта; Ключевые решения (решение+дата, 5–7);
Ссылки. Обновляется перезаписью (не дописыванием). Создаёт командующий при старте
иерархии — и у нового, и при первом появлении нормы в существующем;
ведёт `docs-keeper`: значимая волна → сверка разделов с фактом, расхождение = PROBLEMS.

**Уровни.** Главнокомандующий (оркестратор сессии) держит цель + граф
фронтов + итоговую приёмку; сырые отчёты не читает. **Запуск наблюдателя
и прокурора (командующий):** наблюдатель (`meta/front-observer`) — на
контрольных точках между волнами графа фронтов (после приёмки волны, до
старта следующей); на каждой точке пишет
`fronts/<fid>/observer-heartbeat.txt` (время); приёмка волны требует
свежести метки ≤ **30 мин** (старше — гейт не зелёный, командующий
разбирает); доклады читает командующий; завершение — вердикт
OK / `ПРОБЛЕМА: …` → gate на следующую волну. Прокурор
(`meta/front-prosecutor`) — на каждую волну фронта в иерархии (старт с
волной, до её конца); доклады — только командующему (через его критиков);
генералы канал не читают; завершение — с концом волны / закрытием канала.
Генералы-наблюдатели
(умные субагенты движка, слепые, не исполняют) — 4 прицела: курс фронтов /
швы (контракты-интерфейсы) / правда докладов (выборочный замер) / общая
цель; контрольная точка между волнами графа — следующая волна не стартует
без их OK; власти ноль, только `ПРОБЛЕМА: …` вверх. Генералы фронтов
(умные субагенты движка) — **1 приказ = 1 узкий фронт = 1 генерал** по роли
библиотеки (devops, backend, frontend, данные, QA, безопасность, доки;
архитектура-контракты — всегда первая волна); **пакет задач одному генералу
запрещён** (ошибка командующего; прокурор помечает): свой compass,
декомпозиция 3–7, свои волны через полковников, доклад вверх ВЫЖИМКОЙ
(вердикт + цифры). Несколько задач → несколько генералов параллельно:
масштаб растёт ЧИСЛОМ генералов, не загрузкой одного; волна графа стартует
целиком (параллельно), не по одному.
**Границы волны (мягкие):** в промте каждого генерала — СВОИ пути (свой
runs-каталог фронта) и явный запрет чужих; назначение фронтов —
непересекающееся по работе/файлам (проверка на этапе плана критиками).
Внутри волны непрерывно действует прокурор (`meta/front-prosecutor`);
контрольные точки наблюдателей — между волнами, не вместо прокурора.
**Принцип снайпера:** уровень отвечает только по своему критерию; «нет» →
передача вниз с критерием; чужие нюансы не поднимать и не разбирать здесь.
Генералу при нехватке вариантов — советник (`opportunity-advisor`,
local-cursor): веб копают разведчики (`meta/web-scout`, cloud); советник
предлагает варианты с источниками и оценкой, решение остаётся за генералом;
не путать с researcher (факты) и критиками (проверка).

**Иерархия по подзадачам.** Слои: командующий → генералы фронтов (умные
субагенты движка) → полковники подзадач (cursor, роль `meta/front-colonel.md`)
→ исполнители. Генерал делегирует подзадачи полковникам; полковник командует
кустом работ со свитой. Этап → роль из каталога:

| Этап | Роль |
|---|---|
| Развилка «как делать» | meta/opportunity-advisor.md (local-cursor; веб копают разведчики) |
| Разведка интернета | meta/web-scout.md (запускает советник: local → 2–3 слепых web-scout через cloud) |
| Критика плана | research/fact-checker.md (не-код) / code/code-reviewer.md (код) |
| Исполнение | роли из каталога по домену задачи |
| Приёмка работы | та же красная волна критиков + замер |
| Чтение сырья волн | meta/raw-brief-synthesizer.md (выжимка ≤15 строк командиру) |
| Финальная сшивка отчёта | research/report-synthesizer.md |
| Код-волна (до/после) | code/git-warden.md |
| Значимая волна (доки) | code/docs-keeper.md |
| Значимая код-волна | code/simplicity-warden.md (не усложнили ли) |

**Правило ролей:** роли только из каталога `roles/_index.md`; роли нет →
фабрика по правилам кита (каскад `_index.md` → `_template.md`, «Вдохновлено:
URL» или честная пометка фабрики); импровизированные роли «с головы»
запрещены.

**Рамки полковника:** одна подзадача, 3–5 работ, мини-compass
`fronts/<id>/colonels/<cid>/compass.md` ≤ 4000 символов, один уровень
вложенности (полковник не порождает полковников), 2 неудачных круга →
эскалация генералу. Полковники и исполнители — cursor как обычно (код →
local-cursor CLI, прочее → cloud), слепые, приёмка замером; на границах
работ полковник подтверждает тройку (цель / TODO / следующий шаг через
исполнителей); ремонтный follow-up и dual-path без изменений. Модели:
умные — где решения/проверки множатся; дешёвые — где параллелится труд.

**План тоже через критиков — на КАЖДОМ уровне (закон).** Граф и фронт —
безусловно; план задач — при нетривиальности (как в SKILL/№26):
(а) граф фронтов главнокомандующего → волна критиков плана (умные
    слепые: рёбра, контракты, полнота фронтов, непересечение фронтов по
    работе и файлам (дубли = ошибка графа));
(б) декомпозиция фронта генералом → волна критиков плана фронта;
(в) декомпозиция задач — валидация §3.5 + волна критиков при
    нетривиальности (как в SKILL/№26).
Критики плана видят план + цель уровня, не видят исполнение.
**промт критика/аудитора/наблюдателя:** артефакт + критерий (+ адресат);
без карт локаций и подсказок где искать — проверяющий сам исследует
систему; карта составителя в промте = унаследованное слепое пятно.
Агенты фронтов (субагенты движка) reground-хуков НЕ имеют — их курс держат
compass фронта + контрольные точки наблюдателей.
Генерал может работать столько, сколько нужно задаче — легальна долгая
ОРКЕСТРАЦИЯ (запускает полковников, принимает, докладывает). Запрещено
длительное САМОисполнение: больше 3 подшагов подряд руками делаешь работу
полковника/исполнителя — стоп, вернись к роли и делегируй. Естественные точки сверки —
границы работ (план принят / волна запущена / волна принята / эскалация):
на каждой перечитай compass фронта и подтверди тройку (цель / текущая
строка TODO / следующий шаг через полковников). Оркестратору по часам не рвать
генерала — только по границам работ или при сигнале дрейфа.
Длинный фронт живёт resume-циклами по границам работ (потолок окна ~2 ч): возобновление с compass-фрагментом — штатно, не падение.
Resume-цикл — не разрыв по таймеру и не «рвать по часам»: граница — потолок окна движка, контекст сохраняется.
Исчерпание лимита/квоты на любом уровне = стоп и доклад вверх (владельцу в интерактиве, текстом в авто) — вышестоящий не замещает работу нижестоящего руками; компенсация только разрешёнными механизмами (retry, follow-up, свежий слепой агент). Интерактив — `on_cursor_fail: ask` (спросить раз); если вопросы владельцу недоступны — лестница авто-режима (пауза + доклад текстом + разреженные ретраи). Ручное выполнение работы нижестоящего запрещено.
Ремонт плана = новая волна критиков плана (не ремонтный follow-up артефакта).

**Граф фронтов (контракт, единый с кодом и панелью).** Машиночитаемый
`<state>/fronts.json`:
```
{"goal": str,
 "fronts": [{"id","title","role","deps":[id],"status","compass"}],
 "notes": str}
```
Волны графа = топологический порядок; фронт стартует, когда все deps
приняты (`done`). Статусы: `proposed` / `active` / `stalled` /
`cancelled` / `rejected` / `done`. Статусы `cancelled` / `rejected` —
запуски закрыты; отмена — решение командующего по эскалации / владельцу.
Compass фронта: `<state>/fronts/<id>/compass.md`. Это deps
фронтов — не путать с задачей-DAG (§3): рёбра подзадач по-прежнему в
TODO compass, без `depends_on` в state задач.

**HITL-ворота** — обязательная пауза-вопрос владельцу на: (а) утверждении
графа фронтов; (б) деструктивных действиях (сброс / прод-секреты /
удаление истории); (в) эскалации после 2 кругов — Approve / Revise /
Reject. TTL: нет ответа N мин в интерактиве → лестница авто-режима (как
`on_cursor_fail: ask`); в авто-режиме — безопасная ветка + доклад.

**Эскалация и экономика.** 2 неудачных круга любого уровня → доклад на
уровень выше (не месить). Preflight: главнокомандующий суммирует
прогнозы фронтов; запас на ремонты **+15% на каждом уровне** (как в
SKILL Preflight-бюджет); итог против `execution.ask_before_runs` —
стоп-вопрос владельцу при превышении. Прогоны несут `--front <fid>`;
бюджет — датчик заноса: `warn_runs_per_front` (дефолт **60**) →
churn-сигнал командующему/владельцу без отказа; `hard_runs_per_front`
(дефолт **0** = выкл) — отказ `BUDGET_HARD` только при hard>0; качество >
токены. Лестница авто-режима и слепота волн действуют на каждом уровне без
исключений.

## 4. Волны

Топосорт DAG → волны независимых узлов: базовые/блокирующие → параллельные
независимые → полировка/сшивка. Между волнами — gate: критерии волны зелёные
**замером** + сверка с compass (анти-дрейф). Пишущая волна кода = чекпоинт
`code/git-warden` до + ревизия git-warden после. После значимой волны
(функционал/архитектура/контракты) — обязателен `code/docs-keeper`
(обновление доков → волна критиков); тривиальная — пропуск с пометкой в
compass «доки не тронуты: волна <что> не меняла функционала». После каждой
волны — обнови фазу в compass. Финальная сшивка N артефактов — отдельная
волна синтеза (`report-synthesizer` + критики), не текст оркестратора в
своём контексте. Волна перекрёстной сверки — только на **независимые
источники** (запрет основного источника основных волн в её границах — by
design, не ошибка промта).

## 5. Исполнение и стоп-условия

- Фейл — один repair с уточнённым промтом; второй фейл/завис подряд — стоп
  ветки, доклад владельцу (зелёное уже принятое — сохранить).
- Partial-fail replan: зелёные узлы не перезапускаются; из DAG выкидываются
  только красные и их зависимые; вместо них — новые узлы с уточнённым
  критерием.
- Критики — чистый контекст на дифф/артефакт + критерий (никогда лог).
- Расхождение критиков после кругов — роль синтезатора (reconciliation).
- Финальный отчёт владельцу из N артефактов — `report-synthesizer`
  (не путать с synthesizer/reconciliation).
- Глобальный критерий зелёный → готово; обнови фазу в compass. Пробелы
  покрытия — новая волна (replan DAG), не «донаписать в том же контексте».
  Частые таймауты — ошибка декомпозиции: режь мельче, а не поднимай лимиты.

## Анти-паттерны декомпозиции

- Резать до фиксации цели/критерия (premature decomposition).
- Слишком мелкая нарезка (координация дороже работы).
- Один гигантский шаг («сделай всё») или гигант, порезанный на параллельных
  по неизменяемому состоянию.
- Потеря глобальной цели между волнами (нет сверки с compass).
- Каскад зависимостей там, где были независимые узлы.
- Перезапуск всего DAG из-за одного красного узла.
- Увеличение таймаута вместо replan.
